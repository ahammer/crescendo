## Causes and changes in this PR

**Passive protocol copies can terminate otherwise productive workers.** Service warnings identify
three `notification_payload` overflows, at 09:35:20, 14:12:08 and 21:50:46 UTC, with observed frame
sizes **4,194,759 / 4,531,656 / 4,928,588 bytes**. Two occur before this cycle's deployment and one
after it; the installed earlier output fix therefore did not cover this shape. [L, D]

| Interrupted maintenance run | Recorded wall span / cost | Retained evidence |
| --- | --- | --- |
| Ending 09:35:20 UTC | 70.87m / $3.317548 | Native screenshot/accessibility evidence saved through large file changes; #1204/#1205 already filed. The exact rejected notification method is absent from the log. An accumulated turn diff is a hypothesis, not a confirmed wire capture. |
| Ending 14:12:08 UTC | 3.17m / $0.163653 | Native session records a command and parsed-command copy of roughly 2.18 MB each while serializing retained tracker evidence, with an argument-list failure. |
| Ending 21:50:48 UTC | 53.33m / $3.408526 | Native session records large command/parsed-command copies while saving screenshot evidence. The preceding tool output and evidence remain retained. |

The client already caps supported output deltas and `aggregatedOutput`, but leaves notification
`command`, each `commandActions.command`, file-change `diff` and turn-level aggregated `diff`
uncapped. The native schema confirms these passive fields. Duplicated command text can exceed the
4 MiB notification ceiling even when command output is tiny. This is distinct from the executable
tool/approval request: shortening the later notification cannot change what Codex executed. [C, E, P]

The same regression exercises 4.8 MB diff fields and preserves change path/kind/status. Exact attribution of the first production overflow remains unknown. |
